# SKK の実装を横に並べて比べる：設計

#262 の「進め方」の 1 です。共通の観測の形、[cases.lua](cases.lua) の形と最初の 20 件、実装ごとのキーの表し方の違いを決めます。ドライバはまだ書いていません。次の段（ドライバを書く人）は、この文書と `cases.lua` だけ読めば始められるように書きます。

- 動きの基準は upstream の skkeleton のままです（#220）。この比較は、決めかねているところに「ほかの実装はこうしている」という材料を足すためのものです。
- libskk と DDskk は GPL です。コードも、文書の文も、設定のファイルも、リポジトリに写しません。この文書の libskk と DDskk についての記述は、使い方を覚えている範囲で書いたもので、動かして確かめていません。確かめていないところには「要確認」と付けています。ドライバを書く人が、手元の `help()` や `describe-function` で確かめてください。
- `semantics/core/`（規則の表 `rules.lua`、`CORE.md`、`DECISIONS.md`）は `formal-semantics-task-core` ブランチにあり、まだこのブランチには入っていません。この文書と `cases.lua` は、規則の id と項目の番号を文字として持つだけなので、単独で読めます。

## 0. #262 の前提から変えたこと

1. **ケースは「規則ごと」ではなく「使う人から見た問いごと」に作る。** #262 は「`rules.lua` の規則ごとに 1 つ以上」としていますが、規則の 1〜2 割（95 個のうち 15 個）は skkeleton だけの話で、ほかの実装と比べようがありません（§5）。ケースには「このキー列で何を知りたいか」（`ask`）を書き、規則は印として付けます。規則を覆えたかどうかは、比べられる規則だけで数えます。
2. **観測は、キー列を流し終えたあとの 1 回だけにする。** 1 打ごとの観測は、実装によって取れる時点が違い（表示の更新が 1 打遅れるなど）、ドライバの違いが割れとして出てしまいます。途中を見たいときは、そこで終わるキー列をもう 1 件書きます（C09 と C10 がその形です）。
3. **確定した文字列は、差分ではなく「バッファにあるはずの文字列」で比べる。** `<BS>` や改行の出し方が実装ごとに違うからです。
4. **`expect` は正解ではない。** skkeleton.nvim の今の動きを `CORE.md` の読みから予想したもので、まだ動かしていません。skkeleton.nvim のドライバで `expect` と違ったら、まず `CORE.md` の読みを疑います。ほかの実装が `expect` と違うのは、割れとして記録するだけです。
5. **キーは、skkeleton の既定の割り当てで書き、ドライバが同じ機能のキーに読み替える。** 比べたいのは既定のキーの違いではなく、同じ操作をしたときの動きです。その機能が無い実装では、そのケースは「該当なし」にします。
6. **eskk.vim と skk.vim はこの設計に入れていない。** 入っているかどうか分からないものの形を先に決めません。足すときは、denops 版と同じ「子の nvim に打つ」形（§3.2）がそのまま使えます。

## 1. 全体の流れ

```
cases.lua ──(書き出し)──> .tests/conformance/cases.json
                               │
        ┌──────────────┬───────┴──────┬───────────────┐
   drivers/nvim.lua  drivers/denops.lua  drivers/libskk.py  drivers/ddskk.el
        │              │              │               │
        └──> .tests/conformance/results/<実装>.json <──┘
                               │
                    (比べる) ──> RESULTS.md
```

- 実装が Lua・Python・Emacs Lisp に分かれるので、受け渡しは JSON にします。`cases.lua` から `cases.json` を書き出す処理と、結果を比べて `RESULTS.md` を作る処理は、次の段で Lua で書きます（`nvim -l` で動かす。`vim.json` を使ってよい）。
- 作ったものは全部 `.tests/conformance/` の下に置きます（`.tests/` はリポジトリに入りません）。辞書もここに作り、使う人の辞書（`~/.skkeleton`、`~/.skk-jisyo` など）には触りません。
- ドライバは 1 つずつ順に流します。denops 版は重い処理なので、ほかの人が流していないことを確かめてからにします（`AGENTS.md` の「重い処理」）。

## 2. 観測の共通の形

キー列を流し終えたあとに、次の表を 1 つ作ります。

```lua
{
  text = "漢字",        -- 確定して、バッファにあるはずの文字列。読みや候補（未確定の部分）は入れない
  stage = "select",     -- "none"（読みなし）/ "reading"（▽）/ "select"（▼）/ "register"（辞書登録の欄が開いている）
  reading = "かんじ",   -- 読み。印（▽ ▼ *）と送りと打ちかけは入れない。ひらがなで書く
  okuri = "",           -- 送りのかな。無ければ ""
  pending = "",         -- 打ちかけのローマ字。無ければ ""
  candidate = "漢字",   -- 見えている候補。注釈と印は入れない。候補を見ていなければ ""
  mode = "hira",        -- "hira" / "kata" / "hankata" / "zenkaku" / "abbrev" / "ascii"
}
```

決まり：

- **取れない項目は書かない（`nil`、JSON では項目を省く）。** 比べるときは、両方にある項目だけを比べます。たとえば、候補を見ている間の `pending` は、表示に出ない実装では取れません。
- **`text`** は、流し始めの空のバッファから数えた、確定済みの全部です。改行は `\n` で書きます。
- **`stage = "register"`** のとき、`reading` と `okuri` は登録しようとしている語のものです（欄の中の入力ではありません）。観測のあと、ドライバは欄を取り消して閉じます。
- **`reading`** は、カタカナモードでも ひらがな にそろえます（モードは `mode` で見るため）。abbrev の読みは打った英字のままです。
- **`pending`** は、表示の終わりにある半角の英字です。abbrev のときは英字が全部読みなので、`pending` はいつも `""` にします。
- **`mode`**：`ascii` は、かなを打たない状態をまとめたものです。skkeleton の無効、libskk の latin、DDskk の アスキーモード がここに入ります。`zenkaku` は全角の英字のモードです。
- **辞書への登録**（学習）は、この形には入れていません。確かめたいときは、「確定 → 同じ読みをもう 1 度変換して 1 つ目の候補を見る」というキー列を書きます。

実装ごとの表示の違い（印の文字、モードの名前）を、この形にそろえるのがドライバの仕事です。

## 3. 実装ごとの動かし方

どの実装も、ケースごとに次のようにします。

1. 空のユーザー辞書と、`cases.lua` の `dictionary` から作った辞書のファイルを用意する（§3.5）。
2. 新しい入力の状態を作る（有効、ひらがな、読みなし）。
3. `keys` を切り分けて（§4）、1 つずつ流す。
4. 観測を作る。登録の欄が開いていたら、観測のあとで閉じる。
5. 例外や時間切れは、そのケースの結果に `error` として書き、次のケースへ進む。

設定は、辞書のほかは実装の既定のままにします。使った版（skkeleton.nvim と denops 版はコミット、libskk はパッケージの版、DDskk は clone したコミット、Emacs の版）を結果に書きます。

### 3.1 skkeleton.nvim

`drivers/nvim.lua`。2 通りの動かし方があり、最初の 20 件は core だけで足ります。

- **core だけ**：子の nvim で `tests/core_helpers.lua` の `init_core({ spy_host = true })` を呼び、偽の Library の `data` に辞書を入れ、`require("skkeleton.keymap").handle_key(ctx, key)` に正規化したキー（`require("skkeleton.notation").normalize`）を 1 つずつ渡します。`core_helpers.dispatch` はキーマップを通らないので使いません。
  - `text`：1 打ごとに `ctx.preedit:take_kakutei()` を取り、`\b` は直前の 1 文字を消すものとして、順につなぐ。
  - `stage`：`ctx.state.type == "henkan"` なら `select`、`ctx.state.mode ~= "direct"` なら `reading`、そうでなければ `none`。`host.input` が呼ばれたら（`H.called("input")`）`register`。差し替えた `host.input` は `nil` を返す（取り消し）。`register` のときの `reading` と `okuri` は、`host.input` が呼ばれた時点のものを控えておく。
  - `reading` / `okuri` / `pending`：`ctx.state.henkan_feed` / `okuri_feed` / `feed`。
  - `candidate`：`ctx.state.candidates[ctx.state.candidate_index + 1]` から注釈（`;` より後ろ）を除く。
  - `mode`：`ctx.mode`。`host.disable` が呼ばれていたら `ascii`。
- **E2E**：登録の欄の中の動きなど、本物の `host.input` が要るケースは、§3.2 と同じ形で子の nvim に打ちます。最初の 20 件には要りません。

### 3.2 skkeleton（denops 版）

`drivers/denops.lua`。`tests/diff/driver.lua` の `M.run("denops", child, dict_text, keys, extra, auto_cancel)` をそのまま使います。キー列の切り分け（`M.tokenize`）、1 打ごとに落ち着くのを待つ処理、登録の欄を `<Esc>` で閉じる処理（`auto_cancel`）は、もうあります。deno と denops.vim が無ければ、実装ごと「該当なし」にします（`M.unavailable()`）。

観測は、最後の打鍵のあとのスナップショット（行、カーソル、モード）から作ります。

- 行のうち、▽ か ▼ より前が `text`、後ろが未確定の部分。印の文字は既定（▽ ▼）。
- ▽ があれば `reading`、▼ があれば `select`、cmdline にいて登録のプロンプトが出ていれば `register`。
- 未確定の部分を `*` で分け、前を `reading`（▼ のときは `candidate`）、後ろを `okuri`、終わりの半角の英字を `pending` にする。
- ▼ のときの `reading` は、表示からは取れないので書かない。

skkeleton.nvim の E2E も同じ作り方にします。

### 3.3 libskk

`drivers/libskk.py`。Python の `gi.repository.Skk` を使います。次のことは覚えている範囲で、どれも要確認です。

- 辞書のファイルから辞書を作り、それを渡して入力のコンテキストを作る。ユーザー辞書は一時ディレクトリのファイルにする。
- キーは、空白で区切った文字列をまとめて渡せる。
- 確定した文字列は、溜まった出力を取り出す形で取れる（取り出すと空になる）。未確定の部分は 1 つの文字列で取れ、印（▽ ▼）と `*` を含む。
- 入力モードは列挙の値で取れる（ひらがな、カタカナ、半角カナ、latin、全角の latin）。abbrev が入力モードとして見えるかは分かりません。見えなければ、`mode` は書かず、未確定の部分の形から `stage` だけ作ります。
- 登録の欄は、コンテキストの入れ子として持っている。未確定の部分の文字列に欄の表示が含まれるはずなので、それで `register` を見分ける。

`text` は取り出した出力を順につなぎます。`<BS>` が確定済みの文字を消すとき、libskk は自分では消さず、キーを処理しなかったと返すはずです（要確認）。その場合はドライバが 1 文字消します。

### 3.4 DDskk

`drivers/ddskk.el`。`emacs --batch -Q` で動かします。DDskk は `.tests/conformance/ddskk/` に clone して使い、`load-path` に足します（リポジトリには入れません。clone したコミットを結果に書きます）。次のことも要確認です。

- 個人の設定を読ませないために、DDskk の設定のファイルと辞書の場所を、一時ディレクトリを指す変数で先に決める。辞書の文字コードも変数で UTF-8 にする。
- 一時バッファで SKK のモードを有効にし、キー列をキーボードマクロとして実行する。登録の欄はミニバッファなので、マクロの続きがそのまま欄に入る。
- 観測はバッファの文字列と、DDskk の状態の変数から作る。未確定の部分はバッファの中に印（▽ ▼）つきで入っているので、印より前が `text`。変換の段（読みを打っている / 候補を見ている）と、かなのモード（カタカナ、アスキー、全角、abbrev）は変数で分かる。
- `--batch` では、候補が多いときの一覧（エコーエリア）や、確認の問い（yes / no）が端末を待つことがあります。最初の 20 件は、候補が 2 つ以下で、確認の問いが出ないものにしてあります。

### 3.5 辞書

`cases.lua` の `dictionary` から、SKK の辞書の形のテキストを 1 つ作ります。

```
;; okuri-ari entries.
かk /書/欠/
…
;; okuri-nasi entries.
か /蚊/
…
```

- 文字コードは UTF-8 にし、どの実装にも UTF-8 と伝えます。
- 送りありは見出しの降順、送りなしは昇順に並べます（二分探索をする実装のため）。
- 中身は自分で書いたものです。配布されている辞書（SKK-JISYO.L など）からは写しません。
- ユーザー辞書は、ケースごとに空から始めます。学習で候補の順が変わると、次のケースの結果が変わるからです。

## 4. キーの表し方

`cases.lua` の `keys` は、skkeleton の既定の割り当てを Vim の表記で書いた 1 本の文字列です（`"Kanji<Space><C-j>"`）。`<…>` を 1 つのキーとして切り分けます（`tests/diff/driver.lua` の `tokenize` と同じ決まり）。

| `keys` の書き方 | 意味（機能） | skkeleton.nvim（core） | denops 版 | libskk（要確認） | DDskk（要確認） |
|---|---|---|---|---|---|
| `a`、`K` | 文字、大文字 | そのまま | そのまま | そのまま | そのまま |
| `<Space>` | 変換、次の候補 | `<space>` | `<Space>` | `SPC` | `SPC` |
| `<C-j>` | 確定 | `<nl>` | `<C-j>` | `C-j` | `C-j` |
| `<C-g>` | 取り消し | `<c-g>` | `<C-g>` | `C-g` | `C-g` |
| `<BS>` | 1 文字消す | `<bs>` | `<BS>` | `DEL` か `BackSpace` | `DEL` |
| `<CR>` | 改行 | `<cr>` | `<CR>` | `RET` | `RET` |
| `x` | 前の候補 | そのまま | そのまま | そのまま | そのまま |
| `q` | カタカナ ↔ ひらがな | そのまま | そのまま | そのまま | そのまま |
| `;` | 送りを始める（sticky） | そのまま | そのまま | 既定で効くか分からない | 既定では効かない。効かせる変数がある |
| `/` | abbrev | そのまま | そのまま | そのまま | そのまま |
| `l`、`L` | アスキー、全角の英字へ | そのまま | そのまま | そのまま | そのまま |
| `>` | 接頭辞・接尾辞 | そのまま | そのまま | そのまま | そのまま |
| `<C-q>` | 半角カナ | `<c-q>` | `<C-q>` | 割り当てが違うかもしれない | 割り当てが違うかもしれない |
| `X` | 候補を辞書から消す | そのまま | そのまま | あるか分からない | あるが、確認の問いが出る |
| `<Esc>` | 入力を抜ける | `<esc>` | `<Esc>` | 該当なし（入力の枠の外の話） | 該当なし |

決まり：

- **割り当てが違うときは、同じ機能のキーに読み替える。** 読み替えた表は、ドライバの先頭に 1 つだけ置きます。
- **既定で効かない機能は、設定で効かせてから流す。** DDskk の sticky がそうです。設定を変えたことは結果に書きます。
- **機能そのものが無いときは、そのケースを「該当なし」にする。** 結果には理由を 1 行書きます。割れとしては数えません。
- 表の「要確認」は、ドライバを書くときに 1 つずつ確かめ、確かめた結果でこの表を直してください。

## 5. 比べられる規則、比べられない規則

`rules.lua` の規則のうち、ほかの実装と比べる意味があるものと、無いものを分けます。件数を増やす段（#262 の 3）で「全部覆う」と言うときは、上の段だけを数えます。

| 規則 | 比べられるか | 理由 |
|---|---|---|
| R-IN-*、R-PR-*、R-OK-* | 比べられる | 文字を打つ、▽ を開く、送りを始める。どの実装にもある |
| R-HK-*（R-HK-11 を除く） | 比べられる | 変換、候補の送り戻し、接頭辞・接尾辞 |
| R-CK-*（R-CK-14 を除く） | 比べられる | 取り消し、確定、改行、暗黙の確定 |
| R-MD-* | 比べられる | かなモードの切り替え。abbrev と半角カナは、無い実装では該当なし |
| R-RG-02〜R-RG-06 | 比べられる | 登録の欄の中の動き、登録、取り消し。skkeleton.nvim と denops 版は E2E が要る |
| R-PG-01、R-PG-02 | 一部 | 候補を辞書から消す。確認の問いの出し方が実装ごとに違うので、消したあとの状態だけ比べる |
| R-ST-01 | 比べられる | キー列（`KaNq` など）としては書ける |
| R-EN-*、R-RG-08、R-RG-09 | 比べられない | 有効・無効と、その間の出来事。入力の枠（Vim、IBus、Emacs）の話で、形が違いすぎる |
| R-RG-01、R-RG-07 | 比べられない | `g:skkeleton#mode` と、かなテーブルの持ち方。skkeleton.nvim の中の話 |
| R-HK-11 | 比べられない | `<C-r>=` の式の cmdline。Vim だけの話 |
| R-CK-14 | 比べられない | キー列では起こせない |

## 6. `cases.lua` の形と、最初の 20 件

形は `cases.lua` の先頭に書いてあります。1 件は、`id`、`group`、`keys`、`ask`、`rules`、`views`、`decision`、`expect`、`sure` を持ちます。

最初の 20 件は、次の考えで選びました。

- **ドライバの確かめに 5 件（C01〜C05）。** どの実装でも同じになるはずの、いちばんふつうの入力です。ここで割れたら、実装の違いではなくドライバか辞書を疑います。
- **残りの 15 件は、`DECISIONS.md` で作者に聞いている項目のうち、ほかの実装の動きが材料になるものから。** 欄の中のモードの表示（項目 8）や、かなテーブルの漏れ（項目 7）のように skkeleton.nvim の中だけの話は、比べても材料にならないので入れていません。
- **1 件で 1 つの問い。** 問いは `ask` に、使う人の言葉で書いています。
- **ドライバを書きやすいものだけ。** 候補は 2 つ以下、確認の問いは出ない、登録の欄は開くだけで中には打たない（C14 だけが開きます）。

| 組 | 件 | 何を見るか | `DECISIONS.md` の項目 |
|---|---|---|---|
| baseline | C01〜C05 | かな、変換、確定、次の候補、送りあり | — |
| pending | C06〜C10 | かなにならない打ちかけの行き先（次の子音、`<C-j>`、`<Space>`） | 1、2 |
| okuri | C11〜C14 | 送りの前の n と促音、促音で始まる送り、空の送り | 10 |
| cancel | C15〜C18 | ▼ の `<C-g>`、`<BS>`、`x`、文字 | 14、15 |
| mode | C19、C20 | 確定のあとのモード（カタカナ、abbrev） | 9、18 |

20 件に入れなかったもので、次に足すとよいもの：

- ▽ 送りでの `>`（項目 11）と、▽か*n での `q`（項目 12）。
- 登録の欄の中の動き（欄の中の `<C-g>`、項目 13）。登録して確定する、入れ子にする。
- 改行（`<CR>`）と、確定のあとのモード（全英で改行、など）。
- 接頭辞・接尾辞、候補の一覧（7 つずつ）。一覧は `--batch` の DDskk で止まらないかを先に確かめる。

## 7. 結果の形

ドライバは、`.tests/conformance/results/<実装>.json` に次の形で書きます。

```json
{
  "impl": "libskk",
  "version": "（版かコミット）",
  "settings": { "sticky": "有効にした" },
  "results": {
    "C01": { "observe": { "text": "あいうえお", "stage": "none", "mode": "hira" } },
    "C14": { "na": "sticky が無い" },
    "C16": { "error": "時間切れ" }
  }
}
```

`RESULTS.md` は、ケースごとに 1 行、実装ごとに 1 列の表にします。

- 全部の実装で同じなら「同じ」。
- 割れたら、割れた項目（`text`、`stage` など）と、実装ごとの値を書く。`views` と `decision` を横に並べる。
- skkeleton.nvim が `expect` と違ったら、割れとは別の印を付ける（`CORE.md` の読みを直す必要がある）。
- `na` と `error` は、割れとして数えない。
